## L16 Playwright 기초

**목표**: Playwright로 핵심 사용자 흐름을 E2E로 검증한다.

**이론 핵심**
- E2E는 적게, 핵심 흐름만 (테스트 피라미드)
- locator: `page.getByRole`, `getByLabel` — RTL과 같은 철학
- 자동 대기: `await expect(locator).toBeVisible()`는 조건이 맞을 때까지 기다린다. `waitForTimeout`은 쓰지 않는다
- `webServer` 설정으로 테스트 전에 앱을 띄운다

**실습**
1. 설정: Playwright 설치, `playwright.config.ts`, `pnpm e2e` 스크립트 (학습자가 문서를 보고 직접).
2. [TDD] E2E 먼저 작성 → 페이지 연결: "구독 등록 → 목록에 보임 → 월 합계 갱신".
3. [TDD] "구독 삭제 → 목록과 합계에서 사라짐".

**통과 기준**
- `pnpm e2e` 로컬 통과
- 테스트 코드에 `waitForTimeout`, CSS 선택자가 없다

**면접 질문**: "E2E 테스트는 어떤 시나리오를 골라서 작성하나요?"

## L17 흔들리지 않는 E2E

**목표**: E2E가 불안정해지는 원인(데이터, 순서, 타이밍)을 다룬다.

**이론 핵심**
- 테스트 간 데이터 격리: 테스트마다 초기화, 또는 테스트마다 고유한 데이터
- 테스트 전용 초기화 방법 (예: 개발 환경에서만 열리는 reset 엔드포인트) — 운영에 노출되지 않게
- 실패 분석: trace viewer, 스크린샷, 비디오
- 재시도(retries)는 원인을 숨길 수 있다

**실습**
1. [버그 잡기] Claude가 따로 돌리면 통과하지만 같이 돌리면 실패하는 E2E 2개를 만든다. 학습자는 trace로 원인을 찾고 격리한다.
2. `--repeat-each=5`로 안정성 확인.

**통과 기준**
- `pnpm e2e --repeat-each=5` 전부 통과
- reset 방법이 운영 빌드에서 막혀 있다

**면접 질문**: "E2E 테스트가 불안정할 때 어떻게 대응하나요?"

## L18 접근성 자동 검사

**목표**: 접근성 문제를 자동으로 잡고, 자동 검사의 한계를 안다.

**이론 핵심**
- `@axe-core/playwright`로 페이지 단위 검사
- 자동 검사로 잡히는 것은 일부(색 대비, 라벨 누락, 역할 오류). 키보드 흐름, 포커스 관리는 직접 테스트
- RTL의 역할 기반 쿼리가 이미 접근성 검사를 일부 하고 있다 (L09)

**실습**
1. [버그 잡기] Claude가 페이지에 접근성 문제 3개를 심는다 (라벨 없는 입력, 대비 부족, 버튼이 아닌 클릭 요소). 학습자는 axe 테스트를 먼저 작성해 실패를 확인한 뒤 고친다.
2. 모달(삭제 확인)의 포커스 이동과 Esc 닫기를 직접 테스트한다.

**통과 기준**
- 주요 페이지 axe 위반 0건
- 포커스 관련 테스트 1개 이상

**면접 질문**: "접근성은 어떻게 검증하나요?"

## L19 GitHub Actions CI

**목표**: PR마다 lint, typecheck, 단위·컴포넌트 테스트, E2E가 자동으로 돌게 한다.

**이론 핵심**
- 잡 나누기와 순서: 빠른 검사(lint, typecheck, unit) 먼저, E2E는 따로
- pnpm 캐시, Playwright 브라우저 캐시로 시간 줄이기
- 실패 시 Playwright 리포트를 artifact로 업로드
- Branch protection: 필수 체크 통과 전 머지 금지 (무료 플랜 private 저장소는 제한될 수 있음)

**실습**
1. 학습자가 `.github/workflows/ci.yml`을 직접 작성한다 (Claude는 리뷰만).
2. [버그 잡기] 일부러 실패하는 PR을 만들어 CI가 막는지 확인한다. L01의 커버리지 기준도 CI에서 실패하는지 확인한다.
   - L01에서 나온 아이디어 적용: `coverage-summary.json`의 `total.lines.total`이 0이면 실패하는 검사 스크립트를 만들어 CI에 넣는다. 경로를 일부러 틀리게 바꾼 PR이 막히는지 확인한다.
   - (선택) PR마다 커버리지 표를 댓글로 다는 액션을 붙여 사람이 숫자 변화를 볼 수 있게 한다.
3. CI 실행 시간을 기록하고, 캐시 적용 전후를 비교한다.

**통과 기준**
- PR에서 모든 잡이 초록
- 테스트를 깨뜨린 PR은 머지가 막힌다
- 실행 시간 전후 수치가 PROGRESS.md에 있다
