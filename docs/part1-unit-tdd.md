# Part 1 — 단위 테스트와 TDD (L01 ~ L06)

순수 함수(금액 계산, 결제일 계산)로 테스트의 기본기와 TDD 리듬을 익힌다.
이미 만든 것: `toMonthlyCost`, `toYearlyCost`, `roundWon`, `assertValidAmount`, `InvalidAmountError` (v1 1주차)

## L01 테스트가 진짜 검사하고 있는가

**목표**: 커버리지가 무엇을 말해주고 무엇을 말해주지 않는지 안다. 커버리지 설정 자체가 틀릴 수 있다는 것을 실제 사례로 이해한다.

> 배경 (2026-10-29): `coverage.include`가 `src/domain/**`을 가리켰지만 코드는 `src/app/domain/`에 있어서, 측정 대상이 0개인데도 90% 기준이 통과하고 있었다. 커밋 전에 `include`를 `src/app/domain/**/*.ts`로 고쳤고, 지금은 100%로 측정된다.

**이론 핵심**
- 커버리지 4종류: statements, branches, functions, lines. branches가 가장 정직하다.
- 커버리지는 "실행되었다"는 뜻이지 "검증되었다"는 뜻이 아니다. `expect` 없는 테스트도 100%를 만들 수 있다.
- 기준값(threshold)은 측정 대상이 0개면 통과해버릴 수 있다. 설정 자체도 확인 대상이다.

**예측 질문 예시**
- `expect`가 하나도 없는 테스트로 커버리지 100%가 가능할까?
- `include`에 맞는 파일이 하나도 없으면 90% 기준은 실패할까, 통과할까?

**실습**
1. [버그 잡기] 설정을 수정 전으로 임시로 되돌려 `pnpm test:coverage` 결과를 보고, 왜 0개였는데 기준을 통과했는지 학습자가 설명한다. 확인 후 원래대로 돌려놓는다.
   - (선택) 도메인 코드를 `src/app/domain/` → `src/domain/`으로 옮기기 (App Router의 `src/app/`은 라우팅 폴더). 옮기면 `include`도 같이 바꿔야 한다는 것을 직접 확인한다.
2. [리뷰] Claude가 `expect` 없이 커버리지만 올리는 테스트를 보여주고, 무엇이 문제인지 말하게 한다.
3. 커버리지가 측정 대상이 0일 때 실패하도록 막을 방법이 있는지 스스로 찾아본다 (정답이 하나는 아님. CI에서 막는 방법도 있음).

**통과 기준**
- 수정 전 설정에서 기준이 통과한 이유를 설명할 수 있다
- 테스트 일부를 `it.skip`으로 꺼서 기준 미달로 실패하는 것을 확인했다 (확인 후 되돌림)

**면접 질문**: "커버리지 90%면 테스트가 충분하다고 볼 수 있나요?"

## L02 레드 → 그린 → 리팩터

**목표**: 테스트 하나 → 통과하는 가장 작은 코드 → 정리, 이 리듬을 몸으로 익힌다.

**이론 핵심**
- 레드: 실패하는 테스트 하나. **왜 실패하는지가 예상과 같은지** 확인한다 (import 에러로 실패한 것은 진짜 레드가 아니다).
- 그린: 통과하는 가장 작은 코드. 하드코딩도 괜찮다 (가짜로 구현하기).
- 리팩터: 테스트가 초록일 때만 구조를 바꾼다.
- 다음 테스트는 "지금 구현을 깨뜨릴 수 있는 가장 단순한 예시"로 고른다.

**예측 질문 예시**
- 첫 테스트를 `return '2027-02-15'`로 통과시키는 게 왜 의미가 있을까?

**실습**
1. [TDD] `nextBillingDate(startDate, cycle, today)` — 이번 수업은 **월간 기본 케이스만**.
   - 요구사항: 시작일 기준 다음 결제일을 `'YYYY-MM-DD'`로 돌려준다. 기준일 당일이 결제일이면 다음 회차를 돌려준다.
   - Claude는 함수 시그니처와 빈 파일만 준다. 테스트 목록도 학습자가 먼저 적는다 (TODO 목록 작성 → Claude가 빠진 것 피드백).
   - 테스트 하나마다 레드 확인 → 그린 → (필요하면) 리팩터. 각 사이클에서 무엇을 했는지 한 줄씩 메모.
2. [리뷰] 학습자의 TODO 목록에서 다음에 무엇을 고를지 이유와 함께 말하게 한다.

**통과 기준**
- 월간 기본, 기준일 당일, 시작일이 기준일보다 미래인 경우가 테스트로 있다
- 돌연변이 검사에서 비교 연산자 변형을 잡아낸다
- 테스트 커밋과 구현 커밋의 순서가 맞다 (또는 사이클 메모가 있다)

**면접 질문**: "TDD를 해보셨나요? 그냥 테스트를 나중에 쓰는 것과 무엇이 다른가요?"

## L03 삼각측량과 엣지 케이스

**목표**: 예시를 늘려가며 일반화하고, 날짜 계산의 엣지 케이스를 테스트로 고정한다.

**이론 핵심**
- 삼각측량: 하드코딩으로 통과한 코드를 두 번째·세 번째 예시로 깨뜨려 일반화를 강제한다.
- 경계값: 월말(28/29/30/31), 윤년, 연말 넘어가기.
- 누적 계산의 함정: 1/31 → 2/28 → 3/28 (밀림) vs 매번 시작일 기준 계산 → 3/31.
- JS `Date`의 `setMonth`는 없는 날짜를 다음 달로 넘긴다. 시간대 문제를 피하려면 UTC 기준으로 다룬다.

**예측 질문 예시**
- `new Date(2027, 0, 31)`에 `setMonth(1)`을 하면 어떤 날짜가 될까?
- 1/31 시작 월간 구독의 4번째 결제일은?

**실습**
1. [TDD] L02의 `nextBillingDate`를 확장한다: 월말 보정, 윤년, 날짜 밀림 방지, 연간, 주간.
   - Claude는 요구사항 표만 준다. 구체적인 날짜 예시는 학습자가 고른다.
2. [버그 잡기] Claude가 누적 방식으로 계산하는 별도 구현을 보여준다. 학습자는 그 구현이 실패하는 테스트를 하나 찾아낸다.

**통과 기준**
- 평년 2월, 윤년 2월, 3월 복귀(31일), 연간 2/29 시작, 주간이 모두 테스트되어 있다
- 돌연변이 검사(월말 보정 `Math.min` 제거 등)를 잡아낸다

**면접 질문**: "날짜 계산 로직은 어떻게 테스트하셨나요? 가장 까다로웠던 케이스는?"

## L04 시간을 다루는 테스트

**목표**: "오늘"에 의존하는 코드를 테스트하는 두 가지 방법(인자로 주입, 가짜 시계)을 비교한다.

**이론 핵심**
- 시계 주입: `today`를 인자로 받으면 순수 함수가 되어 테스트가 쉽다.
- `vi.useFakeTimers()` + `vi.setSystemTime()`: 주입할 수 없는 코드(컴포넌트, 서드파티)에 쓴다. 테스트가 끝나면 `vi.useRealTimers()`로 되돌린다.
- 시간에 따라 결과가 달라지는 테스트는 "자정에만 깨지는 테스트"가 된다.

**예측 질문 예시**
- `new Date()`를 함수 안에서 직접 부르는 코드를 12월 31일 밤 11시 59분에 테스트하면 어떤 일이 생길 수 있을까?

**실습**
1. [테스트 리팩터] Claude가 `new Date()`를 직접 쓰는 `daysUntilNextBilling(sub)` 함수와, 실행하는 날에 따라 깨지는 테스트를 준다. 학습자는 가짜 시계로 테스트를 고정한다.
2. [TDD] 같은 기능을 시계 주입 방식으로 다시 설계한다 (예: `daysUntilNextBilling(sub, today)`). 두 방식의 장단점을 말로 정리한다.

**통과 기준**
- 시스템 날짜를 어떤 값으로 바꿔도 테스트 결과가 같다
- 가짜 시계를 쓴 테스트가 다른 테스트에 영향을 주지 않는다 (정리 코드 확인)

**면접 질문**: "현재 시간에 의존하는 코드는 어떻게 테스트하나요?"

## L05 읽히는 테스트

**목표**: 테스트를 명세서처럼 읽히게 만든다. 테스트 냄새를 알아보고 고친다.

**이론 핵심**
- 이름: "무엇을 할 때 → 어떤 결과". 이름만 읽어도 규칙이 보여야 한다.
- `test.each`: 같은 규칙의 여러 예시는 표로. 다른 규칙은 다른 테스트로.
- 테스트 냄새: 한 테스트에 검증이 너무 많음, 테스트 안의 조건문·반복문, 구현을 그대로 베낀 기대값(`expect(f(x)).toBe(x * 52 / 12)`), 의미 없는 매직 넘버, 테스트끼리 공유하는 상태.
- 구현이 아닌 **동작**을 테스트한다.

**실습**
1. [테스트 리팩터] 현재 `billing.test.ts`를 정리한다 (중복된 0원 테스트, `roundWon` 테스트 한 개에 검증 두 개 등은 학습자가 직접 찾는다).
2. [리뷰] Claude가 냄새가 5개 이상 섞인 테스트 파일을 준다. 학습자는 고치기 전에 문제를 목록으로 찾는다.
3. 금액 정책 중 아직 정하지 않은 것(예: 소수 금액 `1.5` 입력)을 정하고 테스트로 고정한다.

**통과 기준**
- 테스트 이름 목록(`pnpm test --reporter=verbose`)만 읽어도 금액 규칙이 설명된다
- 리뷰 문제에서 냄새 5개 중 4개 이상 찾음

**면접 질문**: "좋은 테스트의 기준은 무엇이라고 생각하나요?"

## L06 테스트를 테스트하기

**목표**: 테스트가 버그를 실제로 잡는지 확인하는 방법(돌연변이 테스트)을 안다.

**이론 핵심**
- 돌연변이 테스트: 코드를 일부러 조금 바꿨을 때 테스트가 실패하면 "잡았다", 통과하면 "살아남았다".
- 커버리지 100%여도 돌연변이가 살아남을 수 있다.
- 도구: StrykerJS (`@stryker-mutator/core` + vitest runner). 느리므로 핵심 도메인에만 쓴다.

**실습**
1. [버그 잡기] Claude가 도메인 코드에 버그 3개를 몰래 심는다 (어디에 심었는지 말하지 않음). 학습자는 테스트를 추가해서 3개를 모두 드러낸 뒤 고친다.
2. (선택) StrykerJS를 설치해 `src/domain`에 돌리고, 살아남은 돌연변이를 하나 골라 테스트를 추가한다.

**통과 기준**
- 심은 버그 3개를 모두 테스트로 드러냄
- 각 버그를 잡은 테스트가 무엇인지 말할 수 있다

**면접 질문**: "테스트 코드 자체의 품질은 어떻게 판단하나요?"
