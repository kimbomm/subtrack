- **진행 중인 문제**: L03 실습 2 [버그 잡기] 누적 방식 구현 (출제 전)

  - 실습 1에서 나온 것: 연간 첫 테스트에 레드 예측값을 기대값으로 넣음(기대값은 요구사항에서), 주간 todo 기대값 오타(11-07), 연간 "2월 말일 가입 = 말일 결제" 함정 재발 → `getCalcBillingDate` 재사용으로 구조적 해결, 버그 ① 수정 후 재현 테스트 누락 → 재지적 후 추가. 주간 삼각측량(5주 이상) 스스로 추가
  - 남은 정리: 안 쓰는 함수(`isDaysInMonth`, `setYyyyMmDd`)와 변수(`TD_*`), "2월에 보정됨" 테스트 이름과 실제 입력(11-30/03-05)이 다름
  - 이번 문제에서 나온 것: 표를 채우기 전에 구현부터 고침 → stash로 예전 구현에 돌려 레드 확인(5개 레드, 3월 복귀 1개는 처음부터 초록). "말일 가입 = 말일 결제"로 잘못 설계 → 규칙 `min(가입일의 일, 그 달 말일)`로 재설계. 테스트 입력에 없는 날짜(2027-02-29)를 넣는 실수

## 복습할 개념

수업 중 헷갈렸던 개념을 여기에 쌓는다. 다음 수업의 예측 질문에 하나씩 섞어서 다시 확인한다.

- [L01] `toBeDefined()`는 `undefined`만 거른다. 0, NaN, null도 통과 (truthy 검사와 혼동했음)
- [L01] `as const`의 역할: 리터럴 타입으로 좁혀서 `BillingCycle` 같은 유니온 타입에 넣을 수 있게 함 (문제의 원인으로 오해했음)
- [L01] 하드코딩 기대값 vs 계산한 기대값: 하드코딩이 나은 이유, 숫자의 출처(요구사항)를 테스트 이름에 드러내기 (처음엔 반대로 이해)
- [L01] `NaN`과의 비교는 항상 false. 화면에 0으로 보이는 값과 실제 값(`"Unknown"`)은 다를 수 있음
- [L02] 숨은 버그(현재 동작이 틀림)와 지켜지지 않는 코드(동작은 맞지만 테스트가 보장 안 함)의 차이 — 정리할 때 두 개를 섞어서 설명함
- [L02] 버그 수정 순서: 재현 테스트 먼저 → 레드 확인 → 수정 → 그린. "테스트 케이스가 많으면 좋다"는 표현이 반복됨 (양보다 어떤 상황을 지키는지)
- [L02] 가드 절(early return) vs else
- [L01] 커버리지는 "실행됨"을 알려줄 뿐 버그 유무를 알려주지 않음 (정리할 때 "버그 분기를 알 수 있다"고 표현함)
