## 답변 초안 작성 (90분)

아래 세 질문에 **직접 쓴 초안**을 만든다. 복사하지 않고, 본인의 경험과 말투로 쓴다.

**질문 1.** 테스트를 단위·컴포넌트·E2E로 어떻게 나눴고, 왜 그렇게 나눴나요?
- 힌트: 피라미드 구조, 실행 속도, 실패 원인 파악, 금액 계산을 단위에 둔 이유

**질문 2.** 금액 계산에서 가장 까다로웠던 엣지 케이스와 해결 방법은 무엇인가요?
- 힌트: 월말 날짜 드리프트, 반올림 정책, 음수 입력, UTC 기준 날짜 처리

**질문 3.** CI를 만들고 나서 무엇이 실제로 달라졌나요? 실패한 경우는 어떻게 처리했나요?
- 힌트: 커버리지 게이트 실험, 의도적 실패, Branch protection, E2E 실패 리포트

**답변 작성 형식 (권장)**
- 한 줄 결론
- 구체적 상황 1~2문장
- 내가 한 판단과 이유
- 결과(수치 또는 확인한 사실)

## 기본기 노트 (30분)

**서버 컴포넌트와 클라이언트 컴포넌트**
- 서버 컴포넌트: 기본값. 데이터 조회와 큰 의존성을 서버에서 처리하고 JS 번들에 포함되지 않는다
- 클라이언트 컴포넌트: `'use client'`. 상태, 이벤트 핸들러, 브라우저 API가 필요할 때
- 경계 원칙: 상호작용이 필요한 말단에만 클라이언트 경계를 둔다. 경계를 위로 올릴수록 번들이 커진다

**브라우저 렌더링 파이프라인**
- HTML 파싱 → DOM과 CSSOM 생성 → 렌더 트리 → 레이아웃(리플로우) → 페인트 → 합성
- 레이아웃을 바꾸는 속성(width, top 등)은 비용이 크고, transform과 opacity는 합성 단계에서 처리되어 비용이 작다

**Core Web Vitals**
| 지표 | 의미 | 기준 (좋음) |
|---|---|---|
| LCP | 가장 큰 콘텐츠가 그려지는 시간 | 2.5초 이하 |
| INP | 사용자 입력에 대한 반응 시간 | 200ms 이하 |
| CLS | 레이아웃이 예기치 않게 움직이는 정도 | 0.1 이하 |

정리 질문: 이 프로젝트에서 LCP를 낮추기 위해 할 수 있는 일 3가지는?
